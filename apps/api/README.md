# @portfolio/api

REST API for the portfolio chatbot. TypeScript, Express, no framework beyond that. Request/stream types come from `@portfolio/shared`; model/server/CORS/agent-limit config comes from `@portfolio/config`; the agent loop and tools come from `@portfolio/agent` and `@portfolio/tools`.

## Running

From the repo root:

```bash
pnpm --filter @portfolio/api dev
```

or just `pnpm start:api` / `pnpm dev` (both apps) from the root. Listens on `http://localhost:3001` by default. Runs directly via `tsx watch` — no separate build step, since nothing consumes compiled output yet (no Lambda deployment exists). `pnpm --filter @portfolio/api typecheck` runs `tsc --noEmit`.

## The agent

Each `/chat` request runs a hand-rolled agent loop (`@portfolio/agent`, per PRD 9.10's 12-factor pattern — no agent framework):

- **Unified reducer state**: one object carries `steps`, `status`, the context event log, and the final answer — the loop is state-in/state-out, unit-tested without mocking HTTP (`packages/agent/src/loop.test.ts`).
- **Owned context window**: the event log (user request, narration, tool calls/results, nudges) is serialized into a project-owned single-turn prompt template every step; the provider's multi-turn message format is never the source of truth.
- **Termination as a semaphore**: the model writes its answer as plain text and calls the `final_answer` control tool in the same response. A response is final if and only if it contains that call. `final_answer` carries only source citations, which are validated against the knowledge base's section headings — invalid citations degrade to an answer without sources, never a failure.
- **Deterministic violation handling**: a response with neither tool calls nor `final_answer` gets a nudge event appended and the loop continues, bounded by `MAX_AGENT_ITERATIONS`; hitting the cap returns a safe fallback error, never a half answer presented as final.
- **Truncation detection**: `stopReason` is captured per step. A `max_tokens` truncation without `final_answer` completes with the partial text (nudging would just retry into the same cap) and logs a loud server-side warning; truncation isn't surfaced to the client yet by design.

Tools (`@portfolio/tools`): `list_projects` and `get_contact_information`, reading deterministically from `knowledge/portfolio.json` (gitignored; copy `knowledge/portfolio.example.json` to start — eventually generated by the Notion Projects sync, issue #5). Tool inputs are Zod-validated, unknown tools are rejected, execution errors become safe tool results (no stack traces), and tool calls per request are capped by `MAX_TOOL_CALLS`.

## Endpoints

### `GET /health`

Returns `{ "status": "ok" }`. Does not call the model.

### `POST /chat`

Body:

```ts
{
  message: string;
  sessionId?: string;       // client-generated; the server never creates or looks one up
  conversation?: Array<{ role: "user" | "assistant"; content: string }>;
}
```

Responds as `text/event-stream` (SSE), one JSON object per `data:` frame:

```ts
{ type: "start"; requestId: string; sessionId: string }
{ type: "token"; value: string }
{ type: "tool"; name: string; status: "started" | "completed" }   // name only — never arguments or results
{ type: "thinking"; status: "started" | "stopped" }               // only on models that emit reasoning deltas (zai.glm-5 does not)
{ type: "source"; source: { id: string; title: string; section?: string } }
{ type: "complete"; conversation: Array<{ role: string; content: string }> }
{ type: "error"; code: string; message: string }
```

The client is responsible for keeping `sessionId` and `conversation` across requests — the API is stateless and never persists conversation state itself.

Non-streaming error responses (400 validation, 429 rate limit) use the PRD 15.2 envelope: `{ error: { code, message, requestId } }`.

## Structure

```text
src/
  server.ts            Wiring only: builds dependencies, mounts middleware/handlers
  middleware/cors.ts       CORS headers, reads @portfolio/config's corsConfig
  middleware/apiKey.ts     Checks X-Api-Key against API_KEY if set (no-op if unset)
  middleware/rateLimit.ts  Per-IP fixed-window limiter on POST /chat
  handlers/            Thin HTTP layer: Zod-validate the request, translate
                        service events to SSE via @portfolio/shared's formatSseEvent
  services/chatService.ts   Session/request ids, running the agent, recording the
                             turn, complete/error events — knows nothing about HTTP
  agent.ts             Composition root: builds the tool registry, Bedrock step,
                        and loop deps from @portfolio/agent + @portfolio/tools
  portfolio.ts         Loads knowledge/portfolio.json (falls back to the example file)
  sources.ts           Derives citable sources from the knowledge base's ## headings
  prompt.ts            Builds the system prompt from prompts/system.md + the knowledge base
  session.ts           Session id generation
  sessionRecorder.ts   Appends each turn to data/sessions/<sessionId>.jsonl
```

## Session logs

Every turn is appended to `data/sessions/<sessionId>.jsonl` (gitignored). This is a local stand-in for what will eventually be a DynamoDB write — it exists so you can see what's actually being asked, not to serve conversation history back to the model.

## Environment variables

See the root `.env.example`. `BEDROCK_MODEL_ID` (default `zai.glm-5`), `BEDROCK_REGION` (default `us-east-1`), `PORT`, `ALLOWED_ORIGIN`, `MAX_AGENT_ITERATIONS` (default 5), `MAX_TOOL_CALLS` (default 8), `RATE_LIMIT_WINDOW_SECONDS`/`RATE_LIMIT_MAX_REQUESTS`, and `API_KEY` all have working defaults (or are disabled) if unset; `AWS_BEARER_TOKEN_BEDROCK` is required — the AWS SDK picks it up automatically, no other AWS credentials or config needed.

`API_KEY`, if set, requires every `POST /chat` request to send a matching `X-Api-Key` header — this is **not** user authentication (recruiters never sign in), just a deterrent against direct abuse of the endpoint beyond CORS. It's not a real secret once it ships in the web client's built bundle.

Conversation history sent by the client is currently unbounded — there's no cap or compaction. See [issue #8](https://github.com/matheusgalvao1/ai-powered-portfolio/issues/8) for the planned design (LLM-only compaction, run after the response so it never delays or hangs a turn, using a separate summarizer call rather than the portfolio agent).
